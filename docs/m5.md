# M5 — Plandalf-style notes and generated flashcards

Vutadex stores a **logical note** containing a type and named fields. The note generates one or more ordinary cards, each with independent FSRS-7 state and append-only review history.

## Commands

```sh
node index.ts note types
node index.ts note add 1 basic "What is SQLite?" "An embedded database"
node index.ts note add 1 reverse "France" "Paris"
node index.ts note add 1 optional-reverse "Spain" "Madrid" "yes"
node index.ts note add 1 cloze "{{c1::Paris}} is in {{c2::France}}." "Europe"
node index.ts note add 1 type-answer "Capital of Italy?" "Rome"
node index.ts note list 1
node index.ts note show 1
node index.ts note edit 1 "Updated question" "Updated answer"
node index.ts note delete 1
node index.ts note delete 1 --yes
```

The `note add` / `note edit` positional fields must match the selected type exactly; `note types` prints the field names. Existing `card add/edit/delete` still work on manually created Basic cards. To edit cards generated from notes, use `note edit` so identities remain stable.

## Built-in types

| Type | Fields | Generated cards |
|---|---|---|
| `basic` | Front, Back | One |
| `reverse` | Front, Back | Two independent directions |
| `optional-reverse` | Front, Back, Add Reverse | One, plus reverse if third field is nonempty |
| `cloze` | Text, Extra | One per distinct `{{cN::answer}}` or `{{cN::answer::hint}}` ordinal |
| `type-answer` | Front, Back | One; typed input before self-rating |
| `multiple-choice` | Prompt, Choices, Correct, Explanation | One; stable choice ID |
| `multiple-select` | Prompt, Choices, Correct, Explanation | One; JSON array of correct IDs |
| `ordering` | Prompt, Items, Explanation | One; canonical item order with stable IDs |
| `image-occlusion` | Image, Masks, Extra | One per positive unique mask ID |

For structured questions, `Choices` and `Items` are JSON arrays of `{"id":"abc","text":"Visible answer"}` objects. Correct single choice is a stable ID such as `abc`, while correct multiple-select is JSON like `["a","b"]`. For ordering, the array order is the correct order. Study prompts accept option numbers or IDs; the self-assigned FSRS grade remains separate from whether the answer was correct.

**Image occlusion:** import a local image first:

```sh
node index.ts media add ./tree.png
node index.ts media inspect "deez-media://sha256:<64-character-hash>"
```

The returned `deez-media://sha256:...` URI identifies stored bytes in Vutadex's local media folder. Valid input is PNG, JPEG, WebP or GIF up to 20 MiB. `Masks` is JSON:

```json
[{"id":1,"x":0.1,"y":0.2,"width":0.2,"height":0.3,"answer":"Root","prompt":"Name this part"}]
```

Coordinates are fractions from 0–1. The terminal uses Plandalf's **textual fallback** showing the URI and mask coordinates; it does not render an image UI. Media is stored locally and is **not** yet included in the planned M6 `.deck` interchange format. Importing decks from Plandalf is also reserved for M6.

## Identity and history safety

Generation keys follow Plandalf conventions: `note:<id>:template:<n>`, `note:<id>:cloze:<n>`, `note:<id>:occlusion:<n>`. Editing a note updates matching card text in place while preserving their card IDs, FSRS schedules, history and due dates. No longer generated cards are **retired** rather than deleted, and their history is retained; if a generation key returns, its old card identity and learning history reappear. Retired cards are excluded from listing, due queues and study sessions, and cannot receive new reviews. Manual cards created before M5 remain unchanged.

SQLite migration from schema v3 to v4 is transactional and idempotent. Deleting a deck still permanently cascades through its cards, notes and personal review data, consistent with the existing M1 behavior.

## Boundary

No custom note template editor, graphical mask viewer, binary attachments in export, or `.deck` import/export in M5. These require a separate capability rather than a misleading promise of interchange compatibility.
